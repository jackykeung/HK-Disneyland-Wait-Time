1. Executive summary

An attacker-accurate map of exactly where and how the official HK Disneyland app gets its live ride wait times — and what the practical, working path to the same data is. The headline finding:

Live ride wait times are NOT delivered over a plain HTTP/REST call. They stream into the app through a Couchbase Lite continuous replication channel from Disney's Sync Gateway over a WebSocket (Blip protocol). There is no anonymous public REST endpoint for it. The app also has a legacy REST layer, but that origin is geo-blocked from non-US IPs.

For a live dashboard, the practical source is a public 5-minute mirror of Disney's own feed (Queue-Times Real Time API), which is exactly what this repo's dashboard consumes.

Public mirror (Queue-Times)→ Your dashboard (live)

3. The wait-time data model

Wait times are stored as Couchbase doc WaitTimeInfo in the finder DB, channel hkdl.facilitystatus.1_0. Fields:

WaitTimeInfo {
  waitMinutes:        int,     // posted standby wait (minutes)
  status:             string,  // e.g. "OPEN"/"CLOSED"/"DOWN"
  statuses:           ...,
  singleRider:        bool,
  fastPassStartTime,  fastPassEndTime, fastPassAvailable,
  lastUpdate:         ISO8601,
  lastOfflineTransition: ...,
  alternateId:        string
}

Future wait times (queue forecasting) arrive on a separate channel hkdl.forecastedwaittimes.1_0. Attraction metadata/land grouping comes from the same DB (hkdl.facilities.1_0), and each facility record carries its own primaryLocation (latitude/longitude) — which is what the dashboard uses to place the ride markers.

4. The real Disney transport (the "source of truth")

4.1 Live wait times — Couchbase replication over Blip

wss://realtime-sync-gw.wdprapps.disney.com/park-platform-pub/_blipsync
  • Protocol: Couchbase Lite continuous PULL replicator via the Blip WebSocket.
  • DB: finder.<version>; channel: hkdl.facilitystatus.1_0.
  • Auth: SessionAuthenticator (session id) or BasicAuthenticator (user+pass) — both from the encrypted assets/environments.bin.
  • Auth gate (verified live): the Sync Gateway returns HTTP 403 Access Denied without a session.

4.2 Config/session bootstrap — encrypted asset

The app loads its runtime environment from assets/environments.bin (and build_config.bin), which contains the syncGatewayUrl, syncGatewayUser and syncGatewayPass. It is AES-256-GCM: key built in code (com.disney.wdpro.commons.security.a.g()), 16 chars from a π-vs-ASCII scheme → B1D1F9H6J3L8N7PQ; IV derived through obfuscated Kotlin helpers (l.g0 / s.L0).

Status of the decryption: the key is fully recovered, and the encrypted blob could be decrypted; the IV construction uses mangled Kotlin-collection shim names that are the one unresolved step. Decrypting it yields the literal syncGatewayUrl + credentials needed to read a real session payload.

6. Practice: the working live source

Because Disney's own origin is authenticated and geo-blocked, the reliable live feed is the Queue-Times Real Time API — a public, no-key, 5-minute mirror of Disney's own park feed:

https://queue-times.com/parks/31/queue_times.json
// park 31 = "Disneyland Hong Kong", lat 22.3133, lng 114.0433, tz Asia/Hong_Kong
// Response: { "lands": [...], "rides": [ {id,name,is_open,wait_time,last_updated}, ... ] }

Verified live pairing (Oct 11, 2026): the feed tracks the official app exactly — Iron Man Experience 30 min, Ant-Man & The Wasp Nano Battle 45 min, Frozen Ever After 70 min — all matching the app at the same moment.

Attribution: free to use; display "Powered by Queue-Times.com" linking to https://queue-times.com/en-US (the dashboard does).

6.1 The CORS problem, and the fix

Queue-Times sends no Access-Control-Allow-Origin header, so a browser page cannot fetch() it directly. Two working options (the dashboard ships both):

  • Same-origin proxy (recommended). A tiny stdlib-only Python server (or an nginx location) forwards the feed and adds permissive CORS + a 60s cache. The page fetches /api/wait-times on its own origin — no CORS, no auth, fast, reliable.
  • Public CORS relay (standalone). api.allorigins.win/get?url=… (JSON-wrapped: unwrap .contents) or api.codetabs.com/v1/proxy?quest=…. Added as a fallback chain so the page also works opened directly from file://. Relays are intermittently unavailable, so they are fallbacks, not the primary path.

7. Usage scenarios

7.1 Live wait-time dashboard (this repo)

  • Single self-contained HTML (index.html) — map + sortable list + stat cards, auto-refresh 60s.
  • Ride coordinates decoded from the official app's finder DB (primaryLocation), so markers sit on the true park layout.
  • Runs alone (relay chain) or behind the proxy; deployed at a private origin.

7.2 Reading Disney's own live channel (requires a session)

To tap the true Disney transport you must (a) decrypt environments.bin to recover syncGatewayUrl/user/pass, then (b) run a Couchbase Lite PULL replicator (or speak the Blip protocol) against _blipsync for channel hkdl.facilitystatus.1_0. This is the authenticated, geo-restricted path — not something a plain curl can do.

7.3 Historical / dashboard parity

The same Queue-Times endpoint family serves per-ride historical wait statistics used for strategy/planning; the real-time endpoint is the one that drives a live board.
